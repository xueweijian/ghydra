## F3 实证续（GUI PAC 流量场景，v1.0.2 排期依据加固)

接管后 CONNECT 采样（v2ray 关、裸网）：

| conn | 上游 | 结果 |
|---|---|---|
| #8 | 192.30.255.255:443 | dial 7000ms i/o timeout（死网段） |
| #9/#10 | 185.199.108.1/.3 | TCP 通、TLS ClientHello 即被 RST（SNI 阻断，wsarecv forcibly closed） |
| #11/#12 | 185.199.111.255 | 同上 RST |
| #13/#14 | 140.82.112.2/.4 | OK @ 1.8s（隔离自愈后命中健康 IP） |

- 关键缺陷形态：**单次 CONNECT 只派一个上游，dial 超时/copy RST 后不换 IP 重试**；池内死 IP（192.30.x 网段 + SNI 阻断的 185.199.x）占比高 → 用户侧失败率 ~88%，熔断器跳闸（`TripWhy=流量失败率 88%`，60s 窗口）；死 IP 靠「连续 3 轮失败才隔离」缓慢出清。
- 健康对照：`curl --resolve github.com:443:20.205.243.166` 直连 200 @ connect 45ms——好 IP 一直在池里（State 3、score 最优），是**选择与重试策略**问题，不是通道问题。
- 建议：v1.0.2 F3（冷启动拨号帽+预热+竞速）范围内补一条「CONNECT 上游失败自动换次选 IP 重试（≤2 次）」；SNI-RST 形态（TCP 通 TLS 死）纳入 F4 计罚观测。
