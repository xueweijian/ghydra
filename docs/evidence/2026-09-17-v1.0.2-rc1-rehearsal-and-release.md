## 自更新闭环（v1.0.1 → v1.0.2，裸网，2026-09-17 11:16）

v1.0.1 setup 覆盖重装 → `ghydra update`（v2ray 关，走 GHydra 自身加速链）：

1. **普通权限运行：被文件系统权限阻断，两次失败**（旧版未受影响，"永不自毁"成立）：
   - `清 staging: unlinkat …\update-staging\checksums.txt: Access is denied`——残留 owner=BUILTIN\Administrators（v1.0.1 发布日 9-15 08:08 创建，Users 仅 Read）
   - 提权删除整个 staging 后重试：`建 staging: mkdir …\update-staging: Access is denied`——Program Files 下普通权限连建目录都不行
   - **定性：Windows self-update 设计缺口（非 v1.0.2 回归）**。NSIS 装机到 Program Files（admin），替换 exe/建 staging 均需提权，update 无提权机制。当年 v1.0.0→v1.0.1「Access is denied」三连败的真根因大概率即此
2. **提权运行（管理员终端，Start-Process -Verb RunAs）：全链路成功**：
   - `[sched] 候选入池 github.com: +20（DoH 1 + meta 20，0.4s）`、`Preflight 完成 github.com: 21 候选`
   - `开始更新 v1.0.2` → 下载三件套 → `更新至 v1.0.2（完成待重启）` → `[selfupdate] v1.0.2 就绪`
   - **`ghydra version` → 1.0.2**；`ghydra.exe.old` 回滚备份在位；serve.json 无（off 状态一致）
3. apply 后 staging 残留三件套未清（checksums/minisig/zip）——下次普通权限清扫会再被 ACL 挡，恶性循环

## 千并发回归（发布后补测，2026-09-17 13:35）

口径：`loadtest --mode connect --concurrency 1000 --rounds 3`（本地假上游回环，与外网无关）。

| 二进制 | 成功率 | p50 | p99 | goroutine | HeapSys |
|---|---|---|---|---|---|
| v1.0.2 | 570/3000（19.00%） | 25.2ms | 252ms | 峰值 1014→回落 3 无泄漏 | 29.7MB |

- **回归红线达成：v1.0.2 相对 v1.0.1 同机同口径无退化（19.00% vs 18.47%，差值在单轮噪声内）**
- 瞬时千并发回环风暴 ~19% 是 Windows 真机环境天花板（非 GHydra 代码问题：v1.0.1 相同）；M0 的 3000 连接 100% 基线为 Linux 沙箱数据（2026-09-12），环境不同不可比
- M1 目标「1000 并发 p99 <1s」达成（252ms）；HeapSys 27–30MB 远低于 120MB 红线
- 真实用户为阶梯模式（M0 已证分批 p99 1.15s），瞬时风暴数字不影响真实使用
